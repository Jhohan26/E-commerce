2. SECRETOS
.env y .env.integracion son privados; .example son plantillas sin secretos.
JWT_SECRET: clave privada local de J, aleatoria, mínimo 32 bytes.
CLIENTES_JWT_SECRET: clave HS256 acordada con F, mínimo 32 bytes.
No copiar claves predeterminadas ni publicar credenciales en Git.
.artifacts/credenciales-modulos.json, bases y Secret reales quedan excluidos.
Base64 en Kubernetes Secret no es cifrado.

3. AUTENTICACIÓN DE USUARIOS
USER_AUTH_MODE=clientes: login delegado a F y validación de JWT externos.
USER_AUTH_MODE=local: demostración independiente, no integración central certificada.
No hay fallback automático de F hacia cuentas locales.
CLIENTES_JWT_ISSUER: emisor exacto acordado con F, obligatorio en modo clientes.
CLIENTES_JWT_AUDIENCE: opcional; debe coincidir si se configura.
Claims requeridos: sub no vacío, iat, exp, iss y role o rol firmado.
Si aparecen role y rol deben coincidir. Algoritmo admitido: HS256.
Roles: cliente, operador, administrador. Solo administrador usa las APIs de bandeja.
Cliente y operador reciben 403. No se acepta como autenticación un rol del cuerpo.
Token ausente, vencido, alterado, emisor incorrecto o claims incompletos: 401.
El ZIP (3) de F aún no firma rol ni emisor. Se rechaza ese token sin inventar datos.
Ver docs/INTEGRACION-CLIENTES.md para los cambios que F debe confirmar.

4. ENDPOINTS
GET / y archivos web: públicos, formulario sin información privada.
GET /health/live: público, proceso HTTP.
GET /health/ready: público; consumidor conectado=200, desconectado=503.
POST /api/auth/login: público limitado, JSON username/password.
En modo clientes envía usuario/password a auth.login de F.
Devuelve access_token, token_type, expires_in, expiresAt, inactivitySeconds y role.
GET /api/auth/session: administrador autenticado.
POST /api/auth/logout: autenticado; revocación en J y eliminación de cookie.
GET /api/notificaciones, /cliente/:clienteId, /:id: administrador.
PATCH /api/notificaciones/:id/leida: administrador; cambia lectura.
POST /api/auth/module-login: cuentas técnicas locales, opcional.
POST /api/eventos: cuenta técnica local autorizada para el evento.
400 JSON/contrato inválido; 401 autenticación; 403 permiso; 404 recurso;
429 limitación de login; 503 dependencia de autenticación no disponible.

5. SESIONES Y CUENTAS
Authorization: Bearer <JWT> en API. Panel: cookie HttpOnly/SameSite Strict.
AUTH_SECURE_COOKIE=false solo para HTTP local; true para HTTPS.
AUTH_IDLE_SECONDS=1800; AUTH_LIFETIME_SECONDS=28800; no extiende el exp de F.
Logout de J no es cierre global en todos los microservicios.
Las contraseñas locales usan scrypt y sal; no hay registro público.
scripts/manage-access.js bootstrap | rotate <cuenta> | disable <cuenta>.
Bootstrap no sobreescribe las cuentas existentes ni cambia sus contraseñas.

6. RABBITMQ: CONTROL DISTINTO DE HTTP
RABBITMQ_URL: URL privada broker/vhost. RABBITMQ_REQUIRE_TLS=true exige AMQPS.
Se valida certificado TLS. No usar el JWT de usuario como contraseña del broker.
RABBITMQ_REQUIRE_EVENT_JWT=false por defecto conserva la integración de eventos.
El administrador del broker debe limitar publicación y consumo por cuenta técnica.
Una cuenta administradora compartida entre grupos no permite aislar productores.
J valida exchange, clave y contrato; no lee colas de operaciones de otros servicios.
JWT técnico por mensaje es opcional, no requisito del docente:
RABBITMQ_REQUIRE_EVENT_JWT=true activa AUTH_RPC_QUEUE=notificaciones.auth.login
y exige headers.Authorization="Bearer <JWT técnico de J>" en eventos.
Coordinar con productores antes de activar; no sustituye el JWT de usuarios de F.
examples/LOGIN-RABBITMQ.md documenta esta extensión opcional.

7. FUENTES, CONTRATOS Y PERSISTENCIA
RABBITMQ_SOURCES:
pedidos_exchange fanout: PedidoCreado.
pagos_exchange topic pago.aprobado/pago.rechazado: PagoAprobado/PagoRechazado.
inventario_exchange fanout: InventarioInsuficiente.
facturacion_exchange fanout: FacturaGenerada.
RABBITMQ_QUEUE=grupo-j.notificaciones. DLQ propia .errores y exchange .errores.exchange.
RABBITMQ_PREFETCH=10; RABBITMQ_RECONNECT_MS=5000; RABBITMQ_HEARTBEAT=30.
RABBITMQ_MAX_MESSAGE_BYTES=262144.
evento, clienteId/pedidoId enteros positivos y fecha ISO obligatorios.
PedidoCreado: total no negativo y productos con productoId/cantidad/precio.
ACK posterior al guardado durable. JSON/origen inválido: DLQ. Duplicados: no recrear.
Fallo de base de datos solicita reentrega, no descarte.
Notificacion conserva datos/lectura; EmailJob conserva reintentos/estado de correo.

8. CONSULTAS A CLIENTES
CLIENTES_RABBITMQ_URL opcional, usa RABBITMQ_URL si está vacío.
CLIENTES_RPC_LOGIN_QUEUE=auth.login; JSON {"usuario":"...","password":"..."}.
Respuesta F actual: status=200 y data.token/data.expira_en_segundos.
CLIENTES_RPC_USERNAME/PASSWORD: cuenta técnica que F asigna a J, privada.
CLIENTES_RPC_QUEUE=cliente.consultar; JSON {"id":<clienteId>} con JWT de F.
Respuesta: status=200, data.id, data.estado=1, data.correo válido.
CLIENTES_RPC_TIMEOUT_MS=10000; replyTo temporal, correlationId, TTL y mandatory.
Token cacheado, renueva una vez tras 401; no hay respaldo anónimo.
Esta conexión de datos no otorga rol administrativo a usuarios.

9. SMTP
EMAIL_ENABLED=true activa trabajos para notificaciones nuevas.
SMTP_HOST=smtp.gmail.com; SMTP_PORT=587; SMTP_SECURE=false con STARTTLS obligatorio.
SMTP_USER, SMTP_PASSWORD, SMTP_FROM se configuran en privado.
EMAIL_INTERVAL_MS=5000; EMAIL_MAX_ATTEMPTS=5; espera creciente.
Estados: pendiente, aceptado por proveedor, fallido, no programado.
accepted no confirma entrega ni lectura. No se garantiza envío exactamente una vez.
El fallo de Clientes/SMTP no elimina la notificación.
